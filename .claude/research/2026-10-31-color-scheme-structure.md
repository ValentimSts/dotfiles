# Author one Base24 palette, render every port

Author each colour scheme as a pair of spec-0.11 **Base24 YAML files** (`dark.yaml`, `light.yaml`), keep them in the existing `color-schemes` Stow package, and render every per-app file from them with a small in-repo Jinja2 generator whose outputs are committed next to the templates. That is the pattern every maturely maintained scheme has converged on: Catppuccin, Rose Pine and Nord keep one machine-readable palette and generate ports from it with a template tool, and Tokyo Night re-emits 46 extras from its Lua palette, while Dracula, Gruvbox, Everforest and Solarized hand-write ports and rely on the palette being frozen ([Catppuccin palette](https://github.com/catppuccin/palette/blob/main/README.md), [tokyonight extras](https://api.github.com/repos/folke/tokyonight.nvim/contents/extras)). Base24 is the only cross-tool interchange format with a written slot-semantics spec, 242 existing schemes, official templates for kitty, waybar, rofi, neovim and VS Code, and distinct bright-ANSI slots, so a scheme written in it is portable for free and nothing about it is bespoke ([tinted-theming/schemes](https://github.com/tinted-theming/schemes), [base24 styling](https://github.com/tinted-theming/base24/blob/main/styling.md)). Matugen, wallust and pywal are the wrong tools for a hand-authored palette: they derive colours from a wallpaper or a seed and let you override, not author; whiskers is locked to Catppuccin's identifiers ([matugen](https://github.com/InioX/matugen), [whiskers overrides](https://whiskers.catppuccin.com/concepts/overrides)). The local audit found that the dotfiles currently run **five unrelated palettes across six consumers** (kitty, waybar, rofi, Hyprland, hyprlock, eww), that e-ink light is written out four times, and that Orange Peel, though complete as a kitty file, has six brown-to-gold "hues" and a bright row that duplicates the normal row, so `git diff`, `ls --color` and starship's red/green semantics cannot be distinguished in it ([local audit, orange-peel/dark.conf](file:///home/val/projects/Personal/dotfiles/color-schemes/.config/color-schemes/orange-peel/dark.conf)). The missing Ricepaper kitty files that the audit flagged have since been restored (commit `063096f`) and the stow script bug that caused the loss is fixed (`c82f1f4`). On the repository question the answer is **no, do not split the schemes into a separate repo now**: they are consumed only by symlink on one machine, Stow already handles that, and every project in the survey that externalised its schemes did so because a build tool (Nix/Stylix), a registry, or other people consumed them by URL; a self-contained package directory can be split out later if one of those triggers appears ([Stylix configuration](https://nix-community.github.io/stylix/configuration.html)).

## Mature schemes keep one data file and publish a role table

The schemes that are still actively maintained as organisations all treat a single palette artefact as the source of truth and everything else as derived. Catppuccin's `palette.json` (version 1.8.0) holds four flavours, each with **26 named colours carrying hex, rgb, hsl and oklch** plus an `accent` boolean, and a separate `ansiColors` block with `normal` and `bright` values per ANSI name; it is published to npm, JSR, CSS, Sass and a dozen language ports ([palette.json](https://raw.githubusercontent.com/catppuccin/palette/main/palette.json), [catppuccin/palette README](https://github.com/catppuccin/palette/blob/main/README.md)). Rose Pine's `palette.json` is 12 roles per variant (base, surface, overlay, muted, subtle, text, love, gold, rose, pine, foam, iris) with `dist/` CSS and Tailwind outputs built from it ([rose-pine palette README](https://github.com/rose-pine/rose-pine-palette/blob/main/README.md)). Nord's source is `src/nord.css` defining `--nord0` to `--nord15`, with the explicit design goal that the numbering "preserves the compatibility for terminal color schemes" ([nord readme](https://github.com/nordtheme/nord/blob/develop/readme.md)). The Vim-born schemes keep the palette inside the editor file as `name: [hex, xterm256]` pairs (Gruvbox's `colors/gruvbox.vim`, Everforest's `autoload/everforest.vim`, Tokyo Night's `lua/tokyonight/colors/storm.lua`), and Dracula alone keeps its canonical palette as a README table backed by a prose spec, which has already produced a value conflict between the README and the website for "Current Line" ([gruvbox.vim](https://raw.githubusercontent.com/morhetz/gruvbox/master/colors/gruvbox.vim), [dracula README](https://github.com/dracula/dracula-theme/blob/main/README.md), [draculatheme.com/contribute](https://draculatheme.com/contribute)). The lesson for a personal scheme is direct: the moment the same values are typed into two files by hand, they drift, which is exactly what the local audit observed with the `#2E331E` Orange Peel cursor leaking into both e-ink waybar CSS files.

Every one of the eight schemes names colours semantically or by hue, never by ANSI index as the primary name, and publishes the ANSI mapping as a secondary artefact. Catppuccin's style guide fixes color0 to Surface 1, color7 to Subtext 0, color8 to Surface 2, color15 to Subtext 1, with the six chromatic slots on Red, Green, Yellow, Blue, Pink and Teal, and **generates its bright row by formula** (dark flavours: lightness x 0.94, chroma + 8, hue + 2) ([Catppuccin style guide](https://github.com/catppuccin/catppuccin/blob/main/docs/style-guide.md)). Tokyo Night computes brights with `Util.brighten` in HSLuv (+0.05 lightness, +0.2 saturation); Gruvbox and Dracula hand-pick a separate bright row; Everforest and Nord reuse the normal values for slots 9 to 14 ([tokyonight util.lua](https://raw.githubusercontent.com/folke/tokyonight.nvim/main/lua/tokyonight/util.lua), [gruvbox-dark.xresources](https://raw.githubusercontent.com/morhetz/gruvbox-contrib/master/xresources/gruvbox-dark.xresources), [everforest.vim](https://raw.githubusercontent.com/sainnhe/everforest/master/colors/everforest.vim)). The shared structural convention is a **monochrome ladder of three to seven background and two to three text steps plus six to fourteen hue accents**, with a published role table in which red is always errors, yellow warnings, green success and strings, blue links and info, and selection is a mid-ladder rung or an accent at 20 to 40 percent alpha ([Catppuccin style guide](https://github.com/catppuccin/catppuccin/blob/main/docs/style-guide.md), [rose-pine palette README](https://github.com/rose-pine/rose-pine-palette/blob/main/README.md), [nordtheme colors](https://www.nordtheme.com/docs/colors-and-palettes)). Light variants are now first-class flavours with their own hand-tuned accents (Catppuccin Latte, Rose Pine Dawn, Dracula Alucard, Everforest light) rather than an inversion of the greyscale ladder; only Solarized and Gruvbox swap the ladder, and only Tokyo Night derives its day style algorithmically ([Catppuccin specs](https://github.com/catppuccin/catppuccin/blob/main/docs/specs.md), [tokyonight day.lua](https://raw.githubusercontent.com/folke/tokyonight.nvim/main/lua/tokyonight/colors/day.lua)). Orange Peel's existing dark and light files already follow this better pattern (two full files, not an inversion), which is worth preserving.

Licensing and metadata are equally uniform. Seven of the eight schemes are MIT (Tokyo Night is Apache-2.0); 196 of the 237 licensed kitty-themes entries and 224 of 306 licensed iTerm2 entries are MIT, with Creative Commons in the low single digits in both collections ([kitty themes.json](https://raw.githubusercontent.com/kovidgoyal/kitty-themes/master/themes.json), [iTerm2 licenses.yml](https://raw.githubusercontent.com/mbadolato/iTerm2-Color-Schemes/master/licenses.yml)). The only per-app metadata header worth reproducing verbatim is kitty's `## name / author / license / upstream / blurb` block, because kitty itself parses it and the `themes` kitten reads it ([kitty-themes template.conf](https://github.com/kovidgoyal/kitty-themes/blob/master/template.conf)). Orange Peel's existing files already carry that block, with one defect: the `## upstream:` URL says `ValentimSts/dotfile` (singular) and names a path that does not exist in the repo.

## Base24 is the interchange format; matugen is a wallpaper tool, not a palette tool

Tinted Theming (the continuation of Base16) is the only cross-tool scheme format with a spec, a builder and a gallery. The live schemes repo holds **360 base16 and 242 base24 files** on its `spec-0.11` branch, pushed 2026-10-27; `tinty` v0.35.0 shipped 2026-10-21; nothing in the org is archived ([tinted-theming/schemes](https://github.com/tinted-theming/schemes), [tinty](https://api.github.com/repos/tinted-theming/tinty)). A spec-0.11 scheme is a YAML file with `system`, `name`, `author`, optional `slug` and `description`, recommended `variant: dark|light`, and a `palette` map of `base00` to `base0F` (base16) or `base00` to `base17` (base24) ([builder.md](https://github.com/tinted-theming/home/blob/main/builder.md)). The slot semantics are written down: base00 is the background and ANSI 0, base01 the status-bar background, base02 the selection background, base03 comments and ANSI 8, base04 secondary foreground, base05 the default foreground and ANSI 7, base06 and base07 the light foregrounds, base08 red (variables, diff deleted, ANSI 1 and 9), base09 orange (constants), base0A yellow (classes, ANSI 3), base0B green (strings, ANSI 2), base0C cyan (regex, escapes, ANSI 6), base0D blue (functions, headings, ANSI 4), base0E magenta (keywords, ANSI 5), base0F brown (deprecated) ([styling.md](https://github.com/tinted-theming/home/blob/main/styling.md)). The decisive point for Val is that **base16 forces ANSI 9 to 14 to equal ANSI 1 to 6**, while base24 adds base10 and base11 (two darker backgrounds) and base12 to base17 (bright red, yellow, green, cyan, blue, magenta) so that "bright colors can have a higher luminosity relative to its non-bright counterpart" ([base24 styling](https://github.com/tinted-theming/base24/blob/main/styling.md)). Orange Peel's duplicated bright row is precisely the base16 limitation, and base24 is the standard way out of it.

Coverage matters because it decides how much template work is left to do. Tinted's official templates cover kitty, alacritty, waybar, rofi, vim and neovim, VS Code, dunst, fzf, tmux and the shell; Hyprland exists only as an unofficial Lua template, qt only as an unofficial qt5ct template, and **starship, swaync and eww are not listed at all** ([tinted-theming/home](https://github.com/tinted-theming/home)). The builder exposes a fixed variable set per slot (`base00-hex`, `base00-rgb-r`, `base00-dec-r` and so on) plus `scheme-is-dark-variant` and `scheme-is-light-variant` booleans for templates that branch on mode ([builder.md](https://github.com/tinted-theming/home/blob/main/builder.md)). Stylix accepts a base16 scheme as a file path, a YAML string or an attribute set, and matugen v4 can emit base16, so a Base24 palette is the one format that reaches both the Nix world and the Material world unchanged ([Stylix options](https://nix-community.github.io/stylix/options/platforms/home_manager.html), [matugen releases](https://github.com/InioX/matugen/releases)).

The Hyprland-rice generators solve a different problem. Matugen (2,091 stars, v4.2.0 on 2026-08-17, in Arch `extra`) is used by end-4 and ML4W; it takes an image or a single seed colour (`matugen color hex "#..."`), produces roughly 50 Material You roles, and lets you overwrite or add palette colours through `[config.custom_colors]` and JSON import, but there is no documented way to hand it a complete hand-authored palette as a scheme ([matugen README](https://github.com/InioX/matugen), [matugen releases](https://github.com/InioX/matugen/releases)). Its official kitty template maps `color1` to `error`, `color2` to `tertiary`, `color3` to `secondary` and `color4` to `primary`, which is a wallpaper-harmony mapping rather than a semantic one ([matugen-themes kitty](https://github.com/InioX/matugen-themes/blob/main/templates/kitty-colors.conf)). Wallust can read a pywal or terminal-sexy file with `wallust cs`, but its template model is exactly `color0..15`, `background`, `foreground`, `cursor`: no UI roles at all ([wallust variables](https://explosion-mental.codeberg.page/wallust/templates/variables.html)). Pywal was archived on 2024-04-26 and the `~/.cache/wal` directory on Val's machine (dated 2025-04-10, containing the Orange Peel light palette) is the fossil of that era; pywal16 is the live fork ([dylanaraps/pywal](https://github.com/dylanaraps/pywal), [eylles/pywal16](https://github.com/eylles/pywal16)). Whiskers (Tera templates, v2.9.0) is "custom-built for Catppuccin"; its overrides only replace existing Catppuccin identifiers, so using it for Orange Peel would mean impersonating the Catppuccin role names ([whiskers overrides](https://whiskers.catppuccin.com/concepts/overrides), [catppuccin/whiskers](https://github.com/catppuccin/whiskers)). HyDE's wallbash and caelestia's CLI are closed pipelines, and a caelestia maintainer said in 2025 "There is no support for custom schemes for now" ([caelestia shell discussion](https://github.com/caelestia-dots/shell/discussions/103)). What the rice ecosystem does teach is the mechanics: templates live next to the app configs, outputs are written to a state directory (caelestia uses `~/.local/state/caelestia/theme/`), and every template carries a post-hook that reloads the app ([caelestia-dots/cli](https://github.com/caelestia-dots/cli), [ML4W config.toml](https://github.com/mylinuxforwork/dotfiles/blob/main/dotfiles/.config/matugen/config.toml)).

The generator itself is therefore an implementation detail that every mature scheme owns privately: whiskers for Catppuccin, bloom for Rose Pine, an in-repo Lua `${var}` expander for Tokyo Night ([tokyonight extra/init.lua](https://raw.githubusercontent.com/folke/tokyonight.nvim/main/lua/tokyonight/extra/init.lua), [rose-pine-bloom](https://github.com/rose-pine/rose-pine-bloom/blob/main/README.md)). The standard is the pattern, not the binary: one data file, one template per app, generated outputs committed beside them, and a check mode that fails when the outputs drift from the templates (whiskers' "Check Mode" is the explicit example). On this machine `python-yaml` 6.0.3 and `python-jinja` 3.1.6 are already installed from `extra`, so a 100-line generator costs no new dependency; `tinty` is not in the official repositories, and installing it would buy tinted's mustache templates for apps you then still have to write Hyprland, hyprlock, swaync, eww and starship templates for.

## Every app in the stack can include a colour file; two need a generated block

Almost every app Val runs has a first-class include, which is what makes a generated-file design clean: the main config never changes, only the included file does. Kitty's `include` resolves `~` and environment variables, and kitty's own `dark-theme.auto.conf` / `light-theme.auto.conf` mechanism picks the file matching the desktop colour scheme ([kitty.conf](https://sw.kovidgoyal.net/kitty/conf/), [themes kitten](https://sw.kovidgoyal.net/kitty/kittens/themes/)). Waybar is GTK 3 CSS, so `@import url("palette.css")` plus `@define-color name #hex` consumed as `@name` is the include, and `reload_style_on_change` watches "the style sheet file or any imported css files"; the repo's waybar already does exactly this with 17 module stylesheets importing one `palette.css` ([GTK 3 CSS](https://docs.gtk.org/gtk3/css-overview.html), [waybar(5)](https://github.com/Alexays/Waybar/blob/master/man/waybar.5.scd), [waybar/style.css](file:///home/val/projects/Personal/dotfiles/waybar/.config/waybar/style.css)). Rofi 2.0 resolves `@import "colors"` against the including file's directory, then `~/.config/rofi/themes/`, then `~/.config/rofi/`, tries `.rasi` then `.rasinc`, offers `?import` for an optional file, and defines globals in a `* { }` block referenced as `@name`; the repo's `config.rasi` already has a dead `// @import ...` placeholder on line 1 and `wallpaper.rasi` already imports `config` for its colours ([rofi-theme(5)](https://github.com/davatorium/rofi/blob/next/doc/rofi-theme.5.markdown), [rofi/config.rasi](file:///home/val/projects/Personal/dotfiles/rofi/.config/rofi/config.rasi)). Hyprland 0.57 is Lua-only; the wiki says you "can (and should!!) split this configuration into multiple files" with `require("myColors")` resolved relative to `hyprland.lua`, each `require` is error-isolated, a missing module throws unless wrapped in `pcall`, and colour fields are typed `string|HL.Gradient` where a gradient is `{ colors = {"rgba(..)", "rgba(..)"}, angle = 45 }` ([Hyprland wiki: Core](https://wiki.hypr.land/configuring/core/), [example hyprland.lua](https://github.com/hyprwm/Hyprland/blob/main/example/hyprland.lua)). Hyprlock still speaks hyprlang and registers its own `source =` handler with glob expansion, so a `$var` file is the include there; hypridle has no colour options ([hyprlock ConfigManager.cpp](https://github.com/hyprwm/hyprlock/blob/main/src/config/ConfigManager.cpp)). Swaync's `style.css` is GTK CSS whose shipped default already begins with `@define-color cc-bg ...; @define-color noti-bg ...`, so a generated file that redefines those names and is `@import`ed from a four-line `style.css` is the whole port; `swaync-client -rs` reloads it ([SwayNotificationCenter](https://github.com/ErikReider/SwayNotificationCenter)). Eww's `eww.scss` is SCSS, so the eight `$bg-color`-style variables that currently hardcode Catppuccin Mocha move to an imported partial ([eww.scss](file:///home/val/projects/Personal/dotfiles/eww/.config/eww/eww.scss)).

Two apps cannot include. Starship has no include directive; a `[palettes.<name>]` table inside `starship.toml` selected by `palette = '<name>'` is the only indirection ([starship config](https://starship.rs/config/)). Val's starship already sidesteps this entirely by using ANSI names (`bold red`, `bright-black`) so that the prompt inherits whatever kitty loaded, which is the right design and costs nothing, provided the ANSI row has real hues ([starship.toml](file:///home/val/projects/Personal/dotfiles/starship/.config/starship.toml)). VS Code's options are `workbench.colorCustomizations` scoped per theme inside `settings.json` (applied live) or a theme extension whose `package.json` contributes a JSON theme with `type`, `colors` and `tokenColors`; `window.autoDetectColorScheme` with `workbench.preferredDarkColorTheme` / `preferredLightColorTheme` then follows the desktop ([VS Code themes](https://code.visualstudio.com/docs/configure/themes), [Color Theme guide](https://code.visualstudio.com/api/extension-guides/color-theme)). Neovim's convention, induced from tokyonight, catppuccin and rose-pine, is one `colors/<name>.lua` entry that follows `vim.o.background`, palettes in `lua/<name>/colors/<variant>.lua`, and `mini.base16` as the shortcut that takes a `base00..base0F` table directly and generates cterm colours ([tokyonight colors/tokyonight.lua](https://github.com/folke/tokyonight.nvim/blob/main/colors/tokyonight.lua), [mini-base16](https://github.com/nvim-mini/mini.nvim/blob/main/doc/mini-base16.txt)). That last option fits a Base24 source exactly: the first 16 slots are the mini.base16 palette.

Live reload is solved per app and belongs in the switch script, not in the templates. Kitty reloads on SIGUSR1 (`auto_reload_config` is on by default) or instantly with `kitten @ set-colors --all --configured <file>` when remote control is enabled; waybar on SIGUSR2 or `reload_style_on_change`; Hyprland reloads when a required file changes or on `hyprctl reload`; swaync on `swaync-client -rs`; GTK apps on a gsettings `color-scheme` change, which is instant on Wayland with `xdg-desktop-portal-gtk` running; rofi and hyprlock simply read their files on the next launch or lock ([kitty remote control](https://sw.kovidgoyal.net/kitty/remote-control/), [waybar(5)](https://github.com/Alexays/Waybar/blob/master/man/waybar.5.scd), [Hyprland wiki: Core](https://wiki.hypr.land/configuring/core/), [Arch wiki: Dark mode switching](https://wiki.archlinux.org/title/Dark_mode_switching)). The light/dark signal is the portal key `org.freedesktop.appearance color-scheme` (1 dark, 2 light); kitty, VS Code, libadwaita apps and Chromium/Brave react to it natively, and darkman (Arch `extra`) exposes it and runs hook scripts in `~/.local/share/darkman/` with `dark` or `light` as `$1` for everything else ([portal Settings](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Settings.html), [darkman.1](https://gitlab.com/WhyNotHugo/darkman/-/blob/main/darkman.1)). The desktop already reports `prefer-dark` via gsettings, which is why kitty's auto file selection works today.

The practical consequence is that anything that colours by meaning rather than by taste (git diff add and delete, `ls` directory versus executable, starship's `bold red` error versus `bold green` success, neovim diagnostics once a base16 colorscheme is used) collapses to indistinguishable golds. Orange Peel also has no waybar, rofi, hypr, eww, nvim or VS Code port, is referenced by no consumer, and its header's upstream URL points at a non-existent `dotfile` repo. Finishing Orange Peel therefore means keeping its neutrals and its gold family as the accent and adding genuinely distinct, warm-biased hues for the other five ANSI pairs, which is precisely the Gruvbox and Everforest recipe (warm red, olive green, dusty blue, plum, sage cyan on a brown or green ground) ([gruvbox-dark.xresources](https://raw.githubusercontent.com/morhetz/gruvbox-contrib/master/xresources/gruvbox-dark.xresources), [everforest palette.md](https://github.com/sainnhe/everforest/blob/master/palette.md)).

## A separate repository buys nothing until a build tool or another person consumes the scheme

None of the eight flagship Hyprland rices keeps a hand-written scheme as a standalone artefact at all: end-4, ML4W, linkfrg and caelestia generate Material palettes through templates that live next to the app configs, JaKooLit vendors 172 kitty theme files inside the dotfiles, and HyDE and caelestia, the two projects with curated named schemes, moved them out, HyDE into a repo with one branch per theme plus a JSON registry of 70 third-party repos it explicitly does not maintain, and caelestia into its CLI's Python package data ([HyDE-Project/hyde-themes branches](https://github.com/HyDE-Project/hyde-themes/branches), [hyde-gallery CONTRIBUTING](https://raw.githubusercontent.com/HyDE-Project/hyde-gallery/master/CONTRIBUTING.md), [caelestia-dots/cli](https://github.com/caelestia-dots/cli)). The pattern lines up by consumer. Stylix wants `stylix.base16Scheme = "${pkgs.base16-schemes}/share/themes/...yaml"` or a path, nix-colors fetched and flake-locked schemes from the base16 repo, and Catppuccin ships a dedicated `catppuccin/nix` consumer: Nix needs a URL and a lockfile, not a directory inside a Stow checkout ([Stylix configuration](https://nix-community.github.io/stylix/configuration.html), [catppuccin/nix](https://github.com/catppuccin/nix)). The organisations' one-repo-per-port topology (catppuccin 362 repos, dracula 524, rose-pine 160) exists to parcel out maintenance: each port has `current-maintainers` and `past-maintainers`, and Catppuccin frames submission as "offering it up for co-maintenance" with "we don't expect you to keep maintaining your port after it's been transferred to us" ([port-creation.md](https://github.com/catppuccin/catppuccin/blob/main/docs/port-creation.md), [ports.yml](https://raw.githubusercontent.com/catppuccin/catppuccin/main/resources/ports.yml)). Tinted Theming went the other way for the same reason: "When spec 0.11 was merged, we put schemes from all systems into one repo to simplify builders" ([tinted-theming/schemes README](https://raw.githubusercontent.com/tinted-theming/schemes/spec-0.11/README.md)). For one person maintaining ten ports, the registry YAML, template READMEs, catwalk previews and per-repo licences are overhead with no consumer.

A submodule would also interact badly with the existing Stow setup. Stow's built-in ignore list skips `.git`, `.gitignore` and `.gitmodules` at any depth, but `^/README.*` and `^/LICENSE.*` are anchored at the package root, so a submodule's README and LICENSE one level down would be symlinked into `~/.config`; a package-local `.stow-local-ignore` replaces the defaults entirely; and tree folding means that if `~/.config/color-schemes/<x>` does not exist yet, Stow links the whole submodule directory, after which `git submodule update` changes what the apps see immediately, while a fresh clone without `--recurse-submodules` stows an empty directory and the scheme is silently missing ([Stow ignore lists](https://www.gnu.org/software/stow/manual/html_node/Types-And-Syntax-Of-Ignore-Lists.html), [Stow installing packages](https://www.gnu.org/software/stow/manual/html_node/Installing-Packages.html)). The audit already saw a dangling `~/.config/color-schemes/ricepaper` link when files went missing; a submodule adds a second way to reach that state. The counter-case is real but narrow: Neovim plugin managers clone a repo, which is why every editor port of every famous scheme is a standalone repository, and the upstream collections accept a single file by pull request rather than a repository (tinted wants one YAML, kitty-themes one `.conf` based on `template.conf`, Gogh one YAML with uppercase hex and a filename matching `name:`, iTerm2 one file plus a mandatory `licenses.yml` entry) ([kitty-themes README](https://github.com/kovidgoyal/kitty-themes), [Gogh CONTRIBUTING](https://raw.githubusercontent.com/Gogh-Co/Gogh/master/docs/CONTRIBUTING.md), [iTerm2 README](https://raw.githubusercontent.com/mbadolato/iTerm2-Color-Schemes/master/README.md)). None of those needs a separate repo either; they need a canonical file with `name`, `author`, `variant` and `#RRGGBB` values, which a Base24 YAML is.

## Recommendation

### Palette format and role set

Author every scheme as **two spec-0.11 Base24 YAML files**, `dark.yaml` and `light.yaml`, each with `system: "base24"`, `name`, `author`, `variant`, `description` and a 24-slot `palette`, exactly as the official `base24/dracula.yaml` is laid out ([base24/dracula.yaml](https://github.com/tinted-theming/schemes/blob/spec-0.11/base24/dracula.yaml)). Do not invent a richer private format: 24 slots are enough for ten apps, the files stay droppable into tinty, Stylix, mini.base16 and the tinted gallery unchanged, and the NixOS Discourse complaint that Catppuccin's base16 port "doesn't even match Catppuccin's original vision" is the cost of squeezing a 26-colour palette into 16 slots after the fact, a cost you avoid by authoring in the slot format from the start ([NixOS Discourse](https://discourse.nixos.org/t/is-something-wrong-with-stylix-catppuccin/73313)). Keep the slot semantics from the styling guide and fix the UI aliases in the templates, not in the palette: `bg = base00`, `bg_alt (status bars, mantle) = base01`, `selection = base02`, `muted (comments, borders) = base03`, `subtle = base04`, `text = base05`, `text_bright = base06/base07`, `error = base08`, `warning = base0A` (with `base09` orange as the constants and secondary-warning colour), `success = base0B`, `info/hint = base0C`, `link = base0D`, `keyword = base0E`, `deprecated = base0F`, `pane_dark = base10`, `pane_darkest = base11`, brights `base12..base17`. The one thing base24 cannot express is which accent a scheme uses for focused UI (active border, selected rofi row, waybar highlight); Catppuccin treats that as a build parameter (`accent` in the whiskers matrix), so do the same: a per-scheme `accent: base09` line in the build manifest, not in the palette file ([whiskers matrix mode](https://whiskers.catppuccin.com/concepts/matrix-mode)). Generate the bright row rather than hand-picking it, using Catppuccin's published formula (lightness x 0.94, chroma + 8, hue + 2 for dark; lightness x 1.09, hue + 2 for light) and then overriding by hand where a value looks wrong; store the final values in the YAML so the file is self-contained ([Catppuccin style guide](https://github.com/catppuccin/catppuccin/blob/main/docs/style-guide.md)). License the package MIT, matching 7 of 8 famous schemes and the org rules you would meet if a port were ever adopted.

### Directory layout

Keep the Stow package and its name; restructure its contents so that sources, templates and generated ports are distinguishable, and move the "which scheme is active" state out of the repo into `~/.local/state`, as caelestia does, so Stow never manages a pointer that changes at runtime.

```
color-schemes/                                  # Stow package (unchanged name, in PKGS_COMMON)
  .config/color-schemes/
    schemes/
      orange-peel/dark.yaml  light.yaml           # canonical Base24, the only hand-edited colour files
      e-ink/dark.yaml  light.yaml
      ricepaper/dark.yaml  light.yaml
      earl-grey/light.yaml
    templates/                                  # one Jinja2 template per app, shared by all schemes
      kitty.conf.j2  waybar.css.j2  rofi.rasi.j2  hyprland.lua.j2  hyprlock.conf.j2
      swaync.css.j2  eww.scss.j2  nvim.lua.j2  vscode-theme.json.j2
    build.yaml                                  # manifest: schemes, per-scheme accent slot, apps
    ports/<scheme>/<dark|light>/<app>.<ext>     # generated, committed (whiskers/Rose Pine pattern)
  .local/bin/color-scheme                       # switch scheme or mode, retarget links, reload apps
scripts/
  build-color-schemes.py                        # generator with --check (existing scripts/ convention)
~/.local/state/color-schemes/active/            # runtime state, not in the repo:
  kitty-dark.conf  kitty-light.conf  waybar.css  rofi.rasi  hyprland.lua ...  -> ports/<scheme>/<mode>/...
```

Delete the flat `e-ink/dark.conf` and `e-ink/light.conf` (byte-identical to the `kitty/` copies), the `e-ink/waybar/*.css` files and `waybar/palette.css` (all become generated outputs), and `kitty/configs/catpuccin.theme.conf` unless Catppuccin Mocha is converted into a fourth scheme, in which case its values go into `schemes/catppuccin-mocha/dark.yaml` and the eww duplicate disappears with it. Everything at the package root other than `README*`/`LICENSE*` is symlinked into `$HOME` by Stow, which is why the generator lives in `scripts/` rather than in the package. Add a README section for the package describing the format, the build command and the switch command, replacing the two stale kitty sentences at README lines 112 to 113.

### Generator

Adopt a **small in-repo Python generator (PyYAML + Jinja2, both already installed from `extra`)**, not matugen, wallust, pywal, whiskers or tinty. It reads `build.yaml`, loads each scheme's two YAML files, exposes every slot in the formats the apps need (`hex`, `hex_stripped`, `rgb` triples, `rgba(...)` for Hyprland, `#rrggbbaa`), plus `variant`, `is_dark`, `name`, `slug` and the manifest's `accent`, renders each template once per scheme and mode into `ports/`, and supports `--check` to diff the rendered output against what is committed so a stale port fails before commit, mirroring whiskers' check mode ([whiskers introduction](https://whiskers.catppuccin.com/getting-started/introduction)). Name the exposed variables after the tinted builder's (`base00_hex`, `base00_rgb_r`, `scheme_is_dark_variant`) so that any template can later be moved to tinty's mustache with a mechanical rename if you ever want its 37 official templates ([builder.md](https://github.com/tinted-theming/home/blob/main/builder.md)). Matugen stays available as a future, separate wallpaper mode: because it can emit base16 since v4.0.0, a wallpaper-derived scheme could be written into `schemes/<wallpaper>/` in the same format and flow through the same templates, which is the cleanest way to get both hand-authored and generated schemes without two pipelines ([matugen releases](https://github.com/InioX/matugen/releases)).

### Finishing Orange Peel

Keep the neutrals (`#1b1e12` / `#e6d5b8` dark, `#fdf8ed` / `#2E331E` light), keep the gold family as the orange, yellow, brown and accent slots, and replace the five fake hues with warm-biased real ones. Once the YAML exists, every port Orange Peel is missing (waybar, rofi, Hyprland, hyprlock, swaync, eww, neovim, VS Code) is one build run, and the same run produces the matching ports for e-ink, Ricepaper and Earl Grey.

### Separate repository: no

Keep the schemes inside the dotfiles as the `color-schemes` Stow package. They are consumed only by symlink on one machine, which is exactly what Stow is for; no Nix flake, Stylix, registry or second person consumes them by URL; a submodule would add the folding, empty-checkout and ignore-list hazards described above on top of a stow script that only just stopped losing files; and the survey found no 2026 rice pulling a colour scheme in as a submodule. Make the package self-contained anyway (its own `LICENSE` under MIT, its own README section, no references into other packages) so that it can be split out with git's history-filtering tools later without untangling. Revisit the decision only if one of four triggers appears: a Nix or Stylix configuration must pin the scheme as an input; a Neovim port is to be installed by a plugin manager from git rather than from a local path; the scheme is used on a machine that does not carry the dotfiles; or an organisation adopts a port. Submitting to tinted-theming, kitty-themes, Gogh or iTerm2 is not a trigger, because each accepts a single file by pull request, and the Base24 YAML is already that file.

## Conclusion

The research reframes the question. "Which generator should I adopt" turns out to be the least important decision, because every mature scheme owns a private one and the generator is a hundred lines; "what is the canonical file" is the decision that determines whether the schemes are portable, and Base24 YAML is the only answer that is simultaneously a published spec, a gallery submission format, a Stylix input, a mini.base16 palette and the thing matugen can emit. The famous schemes' real export is their conventions, not their topology: one data file, semantic slot roles, a published ANSI mapping with an explicit policy for brights, light as a first-class variant, generated ports committed beside their templates, MIT.

For Val's repo specifically, the audit changes the priority order. The expensive-looking part (Hyprland Lua modules, hyprlock variables, a VS Code extension) is mechanical once the YAML exists, while the cheap-looking part, Orange Peel's palette, is the actual design work, because a one-hue pywal extraction cannot carry semantic colour no matter how it is templated. Writing the two Orange Peel YAML files with real hues is therefore the first task; the generator, the `active/` state directory and the darkman hook follow, and the five-palette drift the audit found disappears as a side effect of every consumer reading the same rendered output.
